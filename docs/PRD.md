# AI 공감 다이어리 PRD

- 상태: 승인됨(2026-11-18 신 교수가 「제안안대로 승인」함)
- 승인으로 정해진 것: 10.1절 A(첫 모델 15초, 둘째 모델 10초), 10.2절 A(일기를 저장하고 "분석 대기", 나중에 다시 분석), 10.3절 A(109, 1388), 일기 길이 상한 500자
- 승인 뒤에도 남은 것: 사용자 연령대는 제안안이 없어 정해지지 않음. 1단계 전에 신 교수가 구글 로그인 변수 3개를 `.env`에 넣어야 함(11.1절)
- 작성: product-manager(0단계)
- 근거 문서: `docs/PLAN.md` 1장(요구 사항), 2장(계획 전에 확인한 사실), 4.0절(0단계: PRD), 6장(미결), `CLAUDE.md`

## 1. 결론과 승인 요청

- 이 앱은 구글 계정으로 로그인한 사용자가 한 줄 일기를 쓰면, AI가 감정을 분석하고 공감 메시지를 돌려주며, 사용자가 자기 지난 기록만 볼 수 있게 하는 일기장임. 자해나 극단적 선택 표현이 있으면 공감 메시지와 함께 전문 상담 연락처를 안내함
- 이 PRD를 승인하면 backend-developer가 1단계(뼈대)를 시작할 수 있음
- 승인 전에 신 교수가 여섯 가지를 정해야 함
  - 10장(신 교수가 정할 것)의 세 가지: 안과 장단점을 적음
    - 첫 모델을 기다리는 시간 제한 값: 제안은 첫 모델 15초, 둘째 모델 10초
    - 두 모델이 모두 실패할 때의 동작: 제안은 일기를 저장하고 "분석 대기"로 표시하며 나중에 다시 분석하게 함
    - 안내할 상담 연락처: 제안은 109와 1388
  - 11.1절(가정과 확인 필요)의 세 가지
    - 일기 길이 상한: 가정은 500자
    - 사용자 연령대: 10.3절의 연락처 선택에 영향을 줌
    - 구글 로그인 변수 3개를 `.env`에 넣을 방법: 지금 `.env`에 없음(11.1절)
- 1단계는 PLAN.md 4.0절에 따라 신 교수가 이 PRD를 승인한 뒤에 시작함. "분석 대기" 항목(5.2절)을 만들지는 10.2절의 결정에 따름

## 2. 제품 목표와 범위

### 2.1 목표

- 사용자가 구글 로그인 후 한 줄 일기를 저장하고, 그 일기에 대한 감정 분석과 공감 메시지를 받음
- 사용자가 자기 일기만 다시 읽을 수 있음. 다른 사용자의 일기는 어떤 경로로도 보이지 않음
- 위기 표현이 있는 일기에는 상담 연락처가 반드시 함께 나옴. AI 모델이 모두 실패해도 마찬가지임
- 이 작업은 테스트이므로 기존 데이터에 영향을 주지 않음

### 2.2 비목표

- 일기 수정, 삭제, 공유, 통계 그래프, 알림은 만들지 않음. 9장(범위 밖 기능)에 목록을 적음
- 의료 진단이나 치료를 제공하지 않음. 앱은 공감하고 안내할 뿐이며, 전문 상담을 대신하지 않음

### 2.3 정해진 기술과 배포 조건

- 이 조건은 PLAN.md 1장에서 옮김. PRD에서 바꾸지 않음
  - 프레임워크: Next.js
  - 로그인: Auth.js, 구글 로그인만 사용
  - 저장소: `.env`의 `DATABASE_URL`이 가리키는 Supabase Postgres
  - AI: OpenRouter, 키는 `OPENROUTER_API_KEY`
  - 코드 저장소와 배포: 깃허브 `logistex/ai-empathy-diary-ch7-261118`, Vercel 배포
  - 단계와 일정: PLAN.md 4장(0단계부터 5단계)을 따름. 단계는 신 교수가 "진행하라"고 할 때만 시작함

### 2.4 환경 변수 이름

- `.env`는 열지 않았음. 아래는 변수 이름만 적음
  - `DATABASE_URL`: PLAN.md 1장에 있음
  - `OPENROUTER_API_KEY`: PLAN.md 1장에 있음
  - Auth.js와 구글 로그인용 변수: `AUTH_SECRET`, `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET`(2026-11-18 authjs.dev의 설치 페이지와 Google 공급자 페이지를 읽어 확인함)
  - 이 3개 변수는 `.env`에 없음(2026-11-18 값을 출력하지 않는 스크립트로 변수 이름만 판정함). 옛 이름 `NEXTAUTH_SECRET`, `GOOGLE_CLIENT_ID`도 없음(11.1절)

## 3. 사용자

- 핵심 사용자: 구글 계정이 있고, 하루 한 줄로 감정을 정리하고 싶은 사람
- 사용자가 바라는 것
  - 부담 없이 짧게 쓰고 싶음
  - 쓴 감정에 대해 공감받고 위로받고 싶음
  - 내 일기가 남에게 보이지 않아야 함
  - 힘든 순간에 도움받을 곳을 알고 싶음
- 사용자의 연령대는 정하지 않음. 연락처는 10.3절 안 A(109, 1388)로 정해졌으므로, 1388 안내 문구에 대상(9~24세와 보호자)을 밝힘
- 이번 범위의 사용자는 구글 로그인 사용자 1종류임. 관리자 화면은 만들지 않음

## 4. 기능 요구와 완료 기준

우선순위는 MoSCoW로 표시함. 이번 범위의 기능은 모두 Must임. 근거: PLAN.md 1장의 요구 5개가 모두 목적(배포된 앱에서 쓰고, 공감받고, 기록을 보고, 위기 때 안내받음)에 필요함.

### 4.1 F1: 구글 로그인과 로그아웃 (Must)

- 사용자 이야기: 사용자로서, 내 일기를 나만 보도록 하기 위해, 구글 계정으로 로그인하고 싶음
- 완료 기준
  - 로그인하지 않은 사용자가 일기 화면이나 API에 접근하면 로그인 화면으로 가거나 401을 받음
  - 구글 계정으로 로그인하면 일기 쓰기 화면이 열림
  - 로그아웃하면 다시 로그인 전 상태가 되고, 지난 기록 화면에 접근할 수 없음
  - 구글 외의 로그인 방식은 없음
  - 서버는 모든 요청에서 세션의 사용자 ID를 확인함. 화면에서 보내온 사용자 ID를 믿지 않음

### 4.2 F2: 한 줄 일기 쓰기 (Must)

- 사용자 이야기: 사용자로서, 오늘의 감정을 정리하기 위해, 한 줄 일기를 쓰고 저장하고 싶음
- 완료 기준
  - 일기는 1자 이상 500자 이하임(2026-11-18 신 교수 승인). 빈 일기나 공백뿐인 일기는 저장되지 않고 안내 문구가 나옴
  - 500자를 넘으면 저장되지 않고 안내 문구가 나옴. 서버에서도 같은 검사를 함
  - 일기 한 줄을 저장하면 30초 안에 감정과 공감 메시지가 나옴(F3과 함께 판정함)
  - 저장 중에는 저장 버튼이 중복 제출되지 않고, 진행 중임을 알리는 표시가 나옴
  - 키보드만으로 일기를 쓰고 저장할 수 있음

### 4.3 F3: 감정 분석과 공감 메시지 (Must)

- 사용자 이야기: 사용자로서, 내 마음을 이해받는 느낌을 얻기 위해, 일기에 대한 감정 분석과 따뜻한 공감 메시지를 받고 싶음
- 완료 기준
  - 저장 응답에 대표 감정 1개(한국어 짧은 단어)와 공감 메시지(한국어 1~3문장 정도)가 들어 있음. 허용하는 감정 단어 목록과 메시지 길이는 `docs/CONTRACT.md`에서 정함
  - 정상일 때 응답이 일기 저장 후 30초 안에 화면에 표시됨(평균이 아니라 최대 기준. 6장의 시간 제한 합이 25초이므로 가능함)
  - 어느 모델이 응답했는지 기록됨(5장의 `model_used`)
  - 공감 메시지에는 진단, 처방, 약물 안내가 들어가지 않음(프롬프트 규칙이며, ai-integration-specialist가 시험 예문으로 확인함)
  - 두 모델이 모두 실패했을 때의 동작은 10.2절의 결정을 따름

### 4.4 F4: 지난 기록 보기 (Must)

- 사용자 이야기: 사용자로서, 내 마음의 흐름을 돌아보기 위해, 내가 쓴 지난 일기와 그 감정, 공감 메시지를 보고 싶음
- 완료 기준
  - 로그인한 사용자 본인의 일기만 최신순으로 나옴. 각 기록에 일기 내용, 감정, 공감 메시지, 작성 시각이 있음
  - 사용자 A로 저장한 일기가 사용자 B의 조회에 나오지 않음(시험 코드로 확인함)
  - 다른 사용자의 일기 ID로 요청하면 내용 없이 404 또는 403이 돌아옴
  - 기록이 0건이면 "아직 쓴 일기가 없어요" 같은 빈 상태 안내가 나옴
  - 몇 건까지 한 번에 보여 줄지(예: 최근 30건)는 `docs/CONTRACT.md`에서 정함. 목록 페이지 넘기기와 검색은 만들지 않음

### 4.5 F5: 위기 표현 안내 (Must)

- 사용자 이야기: 사용자로서, 힘든 순간에 바로 도움받을 곳을 알기 위해, 일기에 자해나 극단적 선택 표현이 있으면 상담 연락처를 함께 보고 싶음
- 완료 기준
  - 위기 표현은 2겹으로 찾음(PLAN.md 4.2절의 결정)
    - 첫째, 위기 표현 목록으로 서버에서 찾음. 모델 호출 결과와 무관하게 동작함
    - 둘째, 모델이 위기 여부를 함께 판정함
    - 둘 가운데 하나라도 위기로 판정하면 상담 연락처를 보여 줌
  - 위기 예문 5개와 일반 예문 5개에서 위기 판정이 기대와 같음(ai-integration-specialist가 확인함)
  - 두 모델이 모두 실패해 분석 대기(`pending`)가 된 일기에는, 위기 여부와 상관없이 상담 연락처를 부드러운 문구로 함께 보여 줌(2026-11-18 신 교수 승인, 4단계 QA의 2안). 이유: 위기 표현 목록은 조사와 어미 활용 때문에 놓침을 없앨 수 없음(`docs/qa/recheck.md`). 필요 없는 사람에게 한 번 더 보이는 비용이 필요한 사람에게 안 보이는 비용보다 훨씬 작음
  - 목록에서 검출된 위기 일기는 분석이 성공해도 실패해도 위기 안내를 보여 줌. 목록은 위기 놓침을 줄이는 쪽으로 넓게 둠. 일상 문장에 위기 안내가 한 번 더 붙는 오탐은 받아들임(2026-11-18 신 교수 결정 「넓은 판으로 되돌려라」). 목록이 놓친 위기는 모델 판정이나 분석 대기 안내가 받침
  - 위기 일기에는 공감 메시지와 상담 연락처가 함께 나옴. 연락처는 지난 기록 화면에서 해당 기록을 다시 열 때도 나옴
  - 안내하는 연락처의 번호와 출처는 10.3절의 결정을 따름. 4단계에서 qa-engineer가 공식 자료와 같은지 확인함
  - 위기 표시 때문에 일기 저장이 막히지 않음

## 5. 데이터

### 5.1 저장 위치와 지킬 조건

- 이 작업이 만드는 스키마는 `dr_diary`이고, 그 안의 표 이름은 `dr_entries`임. 마이그레이션 기록이 필요하면 `dr_diary` 안에 따로 둠
- 기존 `diary` 스키마는 절대로 건드리지 않음(2026-11-18 신 교수 지시, PLAN.md 1장). 읽기 밖의 작업(표 추가, 변경, 삭제, 행 쓰기)을 하지 않음. 다른 스키마의 표도 건드리지 않음
  - 앱이 실행하는 모든 SQL과 마이그레이션은 `dr_diary.` 안의 대상만 가리킴
  - 마이그레이션 실행 전에 qa-engineer가 SQL을 읽어 `dr_diary.` 밖의 대상이 없는지 확인하고, 신 교수의 승인 뒤에 실행함
  - 실행 전후로 스키마별 표 수와 기존 표의 행 수를 조회해 같은지 비교함
- 사실 확인(PLAN.md 2장에서 옮김): `dr_` 이름은 데이터베이스에 없음. `diary` 스키마에 `entries`(4행)와 `schema_migrations`(1행)이 있고, `diary_0904` 스키마도 있음(2026-11-18 `DATABASE_URL`로 읽기 전용 접속해 조회한 결과를 PLAN.md에서 옮김. 이 PRD 작성 중에는 데이터베이스에 접속하지 않았음)

### 5.2 `dr_diary.dr_entries`의 항목

| 항목 | 내용 | 비고 |
|---|---|---|
| id | 일기 1건의 고유 식별자 | 기본 키 |
| user_id | 로그인한 사용자를 가리키는 값 | 조회와 저장은 이 값으로 거름. 값의 종류(구글 계정 식별자, 이메일 등)는 1단계에서 Auth.js 공식 문서로 확인함 |
| content | 일기 내용 | 1자 이상 500자 이하(가정) |
| emotion | 대표 감정 | 분석 전이거나 실패하면 비어 있을 수 있음 |
| empathy_message | 공감 메시지 | 분석 전이거나 실패하면 비어 있을 수 있음 |
| is_crisis | 위기 여부 | 목록 판정과 모델 판정 중 하나라도 위기이면 참 |
| model_used | 응답한 모델 | 두 모델 ID 중 하나. 두 모델이 모두 실패하면 비어 있음 |
| created_at | 작성 시각 | 서버가 기록함 |
| analysis_status | 분석 상태(완료, 대기) | 10.2절 안 A가 승인되어 추가함(2026-11-18) |

- 열 이름과 형식의 최종 확정은 1단계의 마이그레이션 SQL에서 함. PRD가 정하는 것은 어떤 정보를 담는가임
- 사용자 정보를 담는 표가 별도로 필요한지는 Auth.js의 세션 방식에 달려 있음. 1단계에서 확인함. 필요하면 `dr_diary` 안에 `dr_` 접두어로만 만들고, 마이그레이션과 같이 신 교수의 승인을 받음
- 개인정보: 일기는 민감한 내용일 수 있음. 일기 내용과 `.env`의 비밀 값을 로그에 남기지 않음(8장)

## 6. AI 모델 호출 순서와 실패 처리

### 6.1 호출 순서

1. 서버가 일기를 받으면, 먼저 위기 표현 목록으로 검사함. 이 검사는 모델 호출 결과를 기다리지 않음
2. 첫 모델 `nvidia/nemotron-3-ultra-550b-a55b:free`를 OpenRouter로 부름. 시간 제한은 10.1절의 결정을 따름(제안은 15초)
3. 첫 모델이 시간 안에 응답하지 않거나 오류를 내면, 둘째 모델 `nvidia/nemotron-3.5-super-vl:free`를 부름. 시간 제한은 10.1절의 결정을 따름(제안은 10초)
4. 모델 응답에서 감정, 공감 메시지, 위기 여부를 꺼내 저장하고 화면에 돌려줌
5. 두 모델이 모두 실패하면 10.2절의 결정을 따름

### 6.2 "실패"의 정의(가정)

- 아래 세 가지를 실패로 보고 다음 모델로 넘어감. 정확한 기준은 ai-integration-specialist가 `docs/CONTRACT.md`에 확정함
  - 시간 제한 안에 응답이 없음
  - OpenRouter가 오류 응답을 돌려줌(호출 한도 초과 포함)
  - 응답이 비어 있거나 감정, 공감 메시지를 꺼낼 수 없는 형식임
- 근거: 두 모델은 무료 모델이며 호출 한도와 응답 지연이 있을 수 있음(PLAN.md 2장). 실제 값은 2단계에서 호출해 확인함. 이 PRD 작성 중에는 모델을 호출하지 않았음

### 6.3 시간 예산

- 완료 기준은 저장 후 30초 안에 결과가 나오는 것임. 제안한 시간 제한의 합(15초 + 10초 = 25초)에 저장과 응답 시간 5초를 더하면 30초임
- 배포 환경의 함수 시간 제한은 Vercel 문서에서 확인함: 유동 컴퓨팅(fluid compute, 기본 켜짐)에서 Hobby 요금제의 기본 최대 실행 시간은 300초임(https://vercel.com/docs/functions/configuring-functions/duration, 2026-11-18 WebFetch로 읽음. 문서의 최종 수정일은 2026-08-24). 신 교수의 Vercel 요금제가 무엇인지는 확인하지 않았음(계정 정보를 조회하지 않았기 때문). 5단계에서 배포 전에 다시 비교함

## 7. 화면 느낌

- 따뜻하고 편안한 일기장(PLAN.md 1장)
- 화면 요구
  - 3개 화면: 일기 쓰기, 결과 보기, 지난 기록 보기. 로그인 화면은 구글 로그인 버튼 1개로 단순하게 만듦
  - 따뜻한 색(크림색 바탕, 부드러운 강조색)과 읽기 편한 글자 크기를 씀. 구체적인 색과 글꼴은 frontend-developer가 정함
  - 문구는 부드러운 한국어 존댓말로 씀. 위기 안내 문구는 걱정을 전하되 겁을 주지 않음
  - 휴대폰 폭(375px)과 데스크톱 폭에서 3개 화면이 깨지지 않음
  - 키보드만으로 일기를 쓰고 저장할 수 있음. 글자와 바탕의 대비가 읽기에 충분함

## 8. 비기능 요구

- 성능: 일기 저장 후 30초 안에 결과 표시(4.2절, 4.3절). 지난 기록 목록은 3초 안에 표시됨(가정이며 5단계 스모크 시험에서 확인함)
- 보안
  - `.env`의 비밀 값은 코드, 로그, 커밋, 화면 쪽 코드에 넣지 않음. `OPENROUTER_API_KEY`는 서버에서만 읽음
  - 모든 조회와 저장은 서버에서 로그인한 사용자의 ID로 거름
  - 일기 내용을 로그에 남기지 않음
- 접근성: 키보드 조작, 글자 대비(7장)
- 오류 처리(4단계 시험 대상): 빈 일기, 아주 긴 일기, 로그인하지 않은 요청, 다른 사용자의 일기 ID로 한 요청, 두 모델 모두 실패
- 확장성: 이번 범위에서는 요구하지 않음. 이유: 테스트 작업임

## 11. 가정, 제약, 리스크

### 11.1 가정과 확인 필요

- 일기 길이 상한은 500자로 정함(2026-11-18 신 교수 승인)
- Auth.js와 구글 로그인에 필요한 변수 3개가 `.env`에 없음(2.4절). 확인 필요: 1단계 전에 신 교수가 구글 OAuth 클라이언트를 만들고, 신 교수가 정한 방법으로 3개 변수를 넣음
- 사용자 연령대는 정하지 않음(3장). 2026-11-18 승인에 제안안이 없었기 때문임. 연락처 결정에는 영향이 없음
- 신 교수의 Vercel 요금제는 확인하지 않았음(6.3절)
- 구글 OAuth 클라이언트 설정(승인된 리디렉션 주소)은 5단계에서 배포 주소를 추가해야 함(PLAN.md 4.5절)

### 11.2 제약

- `.env`는 열지 않음. 비밀 값은 코드, 로그, 커밋, 화면 쪽 코드에 넣지 않음
- Supabase MCP로는 이 데이터베이스를 관리할 수 없음(PLAN.md 2장). 마이그레이션은 `DATABASE_URL`로 직접 실행함
- Next.js와 Auth.js의 현재 사용법은 확인하지 않았음(PLAN.md 2장). 1단계에서 공식 문서로 확인함
