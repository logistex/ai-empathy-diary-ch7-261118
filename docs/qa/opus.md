## 2. 찾은 문제(심각도순)

### 2.1 [높음] 위기 표현 목록이 흔한 활용형을 놓쳐, 두 모델이 실패하면 위기 일기에 상담 연락처가 나오지 않음

- 기대한 동작: 위기 표현이 있는 일기에는 상담 연락처가 반드시 나옴. AI 모델이 모두 실패해도 마찬가지임(PRD 2.1절(목표), 4.5절(F5), PLAN 4.2절의 2겹 검출 결정)
- 실제 동작
  - 실제 호출로 재현함. 일기 "퇴근길에 옥상에 올라가서 뛰어내릴까 한참 생각했다. 이제 다 끝내고 싶다."에 대해 첫 모델은 시간 초과(15,008ms), 둘째 모델은 형식 오류(`bad_format`, 7,054ms)로 실패함. 결과는 `{"status":"pending","isCrisis":false}`임. 이 일기는 저장되지만 화면에 상담 연락처가 나오지 않음(`components/EntryCard.tsx` 77행은 `isCrisis`가 참일 때만 연락처를 보임)
  - 목록 검사만으로도 결정적으로 재현됨. 위기 예문 31개 가운데 19개를 놓침(모델을 부르지 않고 `matchesCrisisList`를 직접 부름)

| 놓친 예문(판정 false) | 원인 |
|---|---|
| 옥상에서 뛰어내릴까, 뛰어내릴 거야 | 패턴 "뛰어내리"의 "리"와 "릴"은 다른 글자(받침 있는 음절은 한 코드 포인트임) |
| 목을 맬까 생각했다, 목 매고 싶다 | "맬"은 "매"를 포함하지 않음. "목 매고"는 "목을"이 없음 |
| 세상을 떠날까 봐 | "떠날"은 "떠나"를 포함하지 않음 |
| 죽는 게 나을 것 같다 | 패턴은 "낫"이며 "나을"과 다름 |
| 다 끝내고 싶다, 그만 살고 싶다, 살 이유가 없다, 살아야 할 이유를 모르겠다 | 목록에 해당 표현 없음("살아갈이유가없"만 있음) |
| 내가 죽었으면 좋겠다, 죽어야겠다, 죽으려고 했다 | 목록에 해당 활용형 없음 |
| 유서를 썼다, 약을 모아 두었다, 수면제를 모으고 있다, 칼로 팔을 그었다, 영원히 잠들고 싶다, I want to die | 목록에 없음 |

- 재현 방법
  1. 모델 없이: `node --import tsx`로 `lib/ai/crisis.ts`의 `matchesCrisisList("옥상에서 뛰어내릴까")`를 부름 → `false`
  2. 실제 호출: `node --env-file=.env --import tsx <스크립트>`로 `analyzeEntryWithModels(위 일기, MODELS)`를 부름. 모델이 실패할 때만 재현되므로 매번 재현되지는 않음. 모델 실패를 주입하려면 두 모델의 `timeoutMs`를 1로 바꿔 부름 → `pending`, `isCrisis: false`
- 근거: `lib/ai/crisis.ts` 6~44행(패턴 목록), 50~53행(`includes`로 부분 문자열만 비교). 실행 출력은 이 보고의 4장 아래 "시험 기록"에 적음
- 영향: 무료 모델 2개가 함께 실패하는 일은 이번 4회 호출 중 1회에서 일어남. 그 1회가 하필 방법과 장소가 담긴 위기 일기였음. 모델이 응답하면 모델이 위기를 판정하므로 이 문제는 두 모델이 모두 실패할 때만 드러남. PRD 11.3절이 "목록이 완전하지 않다는 한계"를 리스크로 적었으나, 놓치는 범위가 흔한 활용형까지 넓음
- 둘째 모델이 형식 오류를 낸 원인은 확인하지 않았음. 응답 원문을 로그에 남기지 않고(설계대로임), 호출 한도 때문에 다시 부르지 않았음
- 개선 제안(담당: ai-integration-specialist)
  - 받침이 붙는 활용을 잡도록 어간 단위로 패턴을 바꿈. 예: "뛰어내리" 대신 "뛰어내" 또는 정규식 `뛰어내[리릴린렸]`, "목을매" 대신 `목[을]?[매맬맸]`
  - 빠진 표현을 더함: "끝내고싶", "그만살고", "살이유", "죽었으면", "죽어야", "죽으려", "유서", "모아두", "팔을그" 등
  - 위 33개 예문을 시험 코드(`tests/`)로 고정해 회귀를 막음

### 2.2 [중간] 빈 일기와 공백뿐인 일기에 안내 문구가 나오지 않음

- 기대한 동작: "빈 일기나 공백뿐인 일기는 저장되지 않고 안내 문구가 나옴"(PRD 4.2절 F2)
- 실제 동작: 저장 버튼이 비활성으로 바뀌고 글자 수 표시가 "500자 남았어요"로만 나옴. 왜 저장할 수 없는지 알리는 문구가 없음. 비활성 버튼은 탭 순서에서 빠지므로, 키보드 사용자는 저장 버튼을 찾지 못하고 이유도 듣지 못함
- 재현 방법: 로그인한 뒤 일기 쓰기 화면에서 아무것도 쓰지 않거나 공백만 씀. 이 재현은 코드를 읽어 판정했으며 화면에서 확인하지 않았음(구글 로그인을 할 수 없음)
- 근거: `components/WriteForm.tsx` 19행(`canSave = length > 0 && ...`), 52~59행(글자 수 표시는 500자를 넘을 때만 경고 문구), 70~72행(`disabled={!canSave}`). 500자 초과일 때는 "N자 넘었어요. 500자까지 쓸 수 있어요."가 나와 기준을 채움
- 개선 제안(담당: frontend-developer): 버튼을 비활성으로 두는 대신 제출 때 "한 글자 이상 써 주세요." 같은 문구를 `role="alert"`로 보이거나, 비활성 버튼 옆에 이유 문구를 둠

### 2.3 [낮음] U+0085만 쓴 일기가 서버 검사를 통과한 뒤 데이터베이스에서 거부되어 500이 됨

- 기대한 동작: 공백뿐인 일기는 400 `invalid_content`(CONTRACT 2.2절)
- 실제 동작: 자바스크립트 `trim()`은 U+0085(NEL)를 지우지 않으므로 `normalizeContent(" \u0085 ")`가 길이 1로 통과함. 데이터베이스의 검사 `content ~ '[^[:space:]]'`(en_US.UTF-8)는 U+0085를 공백으로 보고 거부함(`dr_entries_content_not_blank`). API 순서가 "분석 → 저장"이므로 모델을 최대 25초 부른 뒤 500 "일시적인 오류가 생겼습니다"를 돌려줌
- 반대 방향: U+200B(폭 없는 공백), U+180E만 쓴 일기는 두 검사를 모두 통과해 보이지 않는 일기로 저장됨
- 재현 방법: 롤백하는 트랜잭션 안에서 `insertEntry(tx, "qa-test-user", normalizeContent(" \u0085 "), pending)`를 부름 → 제약 위반. 시험 전후 행 수 6 = 6
- 근거: `lib/types/content.ts` 9~11행, `db/migrations/001_dr_diary.sql` 16~17행, `app/api/entries/route.ts` 27~28행
- 영향: 일부러 넣지 않으면 생기기 어려움. 생기면 무료 모델 호출을 낭비하고 사용자에게 엉뚱한 안내를 보임
- 개선 제안(담당: backend-developer): 서버 검사에서 `\p{White_Space}`와 폭 없는 문자를 함께 지운 뒤 길이를 셈

### 2.4 [낮음] 구글 ID 수정(954272b) 전의 일기 5행이 어느 계정에서도 보이지 않음

- 기대한 동작: 사용자가 쓴 일기는 그 사용자의 지난 기록에 나옴
- 실제 동작: `dr_diary.dr_entries` 6행 가운데 5행(사용자 ID 4개)의 `user_id`가 무작위 UUID 꼴임. 954272b 전에는 Auth.js가 로그인마다 새로 만드는 `token.sub`를 사용자 ID로 썼으므로, 이 행들은 지금의 어느 로그인으로도 조회되지 않음. 이 가운데 위기 행이 있는지는 확인하지 않았음(전체 위기 행은 2개)
- 재현 방법: 읽기 전용 트랜잭션에서 `user_id ~* '^[0-9a-f]{8}-[0-9a-f]{4}-'`인 행 수를 셈 → 5행, 사용자 4명. 구글 `sub` 꼴(숫자)은 1행, 사용자 1명. 행 내용과 ID 값은 출력하지 않았음
- 근거: 커밋 954272b의 `auth.ts` 17~19행 주석, `node_modules/@auth/core/lib/actions/callback/oauth/callback.js` 224행(`id: crypto.randomUUID()`)
- 영향: 개발 중 시험 데이터이므로 실제 사용자 피해는 없음. 다만 주인이 볼 수 없는 일기 내용이 데이터베이스에 남음
- 개선 제안: 배포 전에 이 5행을 지울지 신 교수에게 여쭘(지우기는 되돌릴 수 없으므로 QA가 하지 않음)

### 2.5 [낮음] 구글 ID가 없는 옛 세션에서는 화면은 로그인 상태인데 모든 API가 401을 돌려줌

- 기대한 동작: 사용자 ID가 없는 세션은 로그인 전 상태로 보임(`auth.ts` 26행 주석: "다시 로그인하게 함")
- 실제 동작: `app/page.tsx` 11행은 `session?.user`만 보고 일기 화면과 이름을 보임. `session.user.id`가 빈 문자열이면 `getUserId()`가 `null`이므로 API는 401임. 사용자는 이름과 로그아웃 버튼이 보이는 화면에서 "로그인이 풀렸어요. 다시 로그인해 주세요."를 받고, 스스로 로그아웃한 뒤 다시 로그인해야 함
- 재현 방법: 954272b 전에 로그인해 받은 세션 쿠키로 접속함. 이 쿠키가 없어 실제로 재현하지 못했고, 코드를 읽어 판정함
- 근거: `auth.ts` 27~30행, `lib/auth/get-user-id.ts` 9행, `app/page.tsx` 11행
- 영향: 954272b 전에 로그인한 개발자 브라우저에만 해당함. 세션 만료(기본 30일) 전까지 남음
- 개선 제안(담당: backend-developer): `page.tsx`에서 `session?.user?.id`로 판정함

### 2.7 [낮음] 다시 분석 API에 UUID가 아닌 ID를 보내면 일기 길이 안내가 나옴

- 기대한 동작: CONTRACT 2.4절대로 400 `invalid_content`이면서, 사용자에게 보여 줄 수 있는 맞는 문장
- 실제 동작: 메시지가 "일기는 1자 이상 500자 이하로 써 주세요."임. 화면도 400을 같은 문장으로 바꿈(`components/diary-api.ts` 9행)
- 재현 방법: 로그인한 상태에서 `POST /api/entries/not-a-uuid/reanalyze`. 로그인할 수 없어 코드를 읽어 판정함(비로그인 상태에서는 401이 먼저 나옴을 `curl`로 확인함)
- 근거: `app/api/entries/[id]/reanalyze/route.ts` 19행, `app/api/entries/http.ts` 6~9행
- 영향: 화면은 서버가 준 UUID만 보내므로 정상 사용에서는 생기지 않음

### 2.8 [낮음] 모델 응답 뒤에 중괄호가 든 설명이 붙으면 올바른 JSON도 실패로 처리함

### 2.9 [낮음] `lib/ai`에 `server-only` 가드가 없고, 일기에 `</diary>`를 넣어 프롬프트 구분을 벗어날 수 있음

### 3.1 로그인할 때마다 같은 사용자 ID인지

- 판정: 같음
- 근거
  - `auth.ts` 20~25행은 로그인할 때 받는 `account.providerAccountId`를 `token.googleId`에 담고, 30행은 그 값을 `session.user.id`로 씀

  - 로그인 뒤의 요청에서는 `account`가 없으므로 `token`에 이미 담긴 `googleId`가 그대로 유지됨(`jwt` 콜백이 `token`을 그대로 돌려줌)

- CSRF: API는 `Content-Type`을 검사하지 않지만, 세션 쿠키가 `SameSite=Lax`(`@auth/core/lib/utils/cookie.js` 52행)이므로 다른 사이트의 POST에는 쿠키가 붙지 않음. 문제로 세지 않음

### 4.1 시험 기록

- 실제 모델 호출(시각은 2026-11-18 13시 무렵 KST)
  1. 첫 모델 시간 제한 1ms 주입 → 둘째 모델 응답. 첫 모델 `timeout` 27ms, 둘째 모델 `ok` 5,550ms, 감정 기쁨. 1ms로 끊은 첫 요청이 OpenRouter에 닿았는지는 확인하지 않았음(닿았다면 호출 수는 5회임)
  2. 목록에 걸리는 위기 일기 → 첫 모델 `ok` 4,894ms, 감정 슬픔, `isCrisis: true`
  3. 목록에 안 걸리는 위기 일기 → 첫 모델 `timeout` 15,008ms, 둘째 모델 `bad_format` 7,054ms, `pending`, `isCrisis: false`
- 대역 `fetch` 시험 17개: 정상 JSON, 코드 블록 안 JSON, 감정 앞뒤 공백, 150자 메시지, `crisis`가 문자열이거나 빠짐(→ `false`)은 `completed`. HTTP 429, `error` 본문, 빈 응답, `null` 응답, JSON 아님, 목록 밖 감정, 151자, 공백 메시지, HTML 본문, 네트워크 예외, 뒤에 중괄호가 붙은 설명은 두 모델 모두 실패 후 `pending`
- 비로그인 `curl`: `GET /api/entries`, `POST /api/entries`(빈 일기, 공백, 정상, 501자, JSON 아님, `userId` 위조), 다시 분석(UUID 아님, UUID), 위조 세션 쿠키 2개 → 모두 401과 `{"error":{"code":"unauthorized",...}}`. 다시 분석 `GET`과 `DELETE /api/entries` → 405
- 데이터베이스: 읽기 전용 트랜잭션으로 행 수, ID 꼴, 권한, RLS를 조회함. 쓰기는 롤백하는 트랜잭션에서만 했고 전후 행 수가 6 = 6임. `diary` 스키마는 행 수만 읽음
- 이 시험을 위해 만든 스크립트는 작업 폴더 밖의 임시 폴더에 둠. 데이터베이스 조회 스크립트 1개는 `postgres` 모듈을 찾게 하려고 작업 폴더에 잠시 복사해 실행한 뒤 바로 지웠음
