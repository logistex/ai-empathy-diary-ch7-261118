# AI 공감 다이어리 개발 계획

- 목적: 구글 계정으로 로그인한 사용자가 배포된 앱에서 한 줄 일기를 쓰고, 감정 분석과 공감 메시지를 받고, 자기 지난 기록만 볼 수 있음. 위기 표현이 있으면 전문 상담 연락처를 함께 봄
- 따를 결정: 신 교수의 2026-11-18 요청(이 문서 1장), 이 폴더의 `CLAUDE.md`(한국어, `.env`는 변수 이름만), `.claude/agents`의 에이전트 5개
- 못 할 것: `.env`에 어떤 변수가 있는지 확인하지 못함(이 폴더 규칙상 열지 않음). 그러므로 필요한 변수는 6장(미결)에 이름만 적고 신 교수에게 확인함

## 1. 요구 사항

- 앱은 한 줄 일기에 AI가 감정을 분석하고 공감하며 위로하는 일기장임
  - 사용자: Auth.js로 구글 로그인을 한 사용자. 사용자는 자기 일기만 봄
  - 기능: 한 줄 일기 쓰기, 감정 분석과 공감 메시지, 지난 기록 보기
  - 위기 대응: 일기에 자해나 극단적 선택 같은 표현이 있으면 공감 메시지와 함께 전문 상담 연락처를 안내함
  - 화면 느낌: 따뜻하고 편안한 일기장
- 기술과 배포 대상은 정해져 있음
  - 프레임워크: Next.js
  - 저장소: `.env`의 `DATABASE_URL`이 가리키는 Supabase Postgres. 이 작업은 테스트이므로 `dr_` 접두어를 붙인 `dr_diary` 스키마를 새로 만들고, 그 안의 표에도 `dr_` 접두어를 붙임(예: `dr_diary.dr_entries`)
  - 기존 `diary` 스키마는 정상이며 절대로 건드리지 않음. 다른 스키마의 표도 건드리지 않음(2026-11-18 신 교수 지시)
  - AI 모델: OpenRouter의 `nvidia/nemotron-3-ultra-550b-a55b:free`를 먼저 부름. 응답이 없거나 오류가 나면 `nvidia/nemotron-3.5-super-vl:free`로 넘어감. 키는 `.env`의 `OPENROUTER_API_KEY`
  - 코드 저장소와 배포: 깃허브 저장소 `logistex/ai-empathy-diary-ch7-261118`에 올리고 Vercel에 배포함(2026-11-18 신 교수가 정함)

## 2. 계획 전에 확인한 사실

- 두 모델 ID는 2026-11-18 OpenRouter 모델 목록에 있음(공개 API `GET /api/v1/models`를 조회함)
  - 두 모델 모두 입력 가격이 0이고, 컨텍스트 길이는 1,000,000임
  - 무료 모델은 호출 한도와 응답 지연이 있을 수 있음. 실제 값은 2단계에서 호출해 확인함
- `DATABASE_URL`이 가리키는 데이터베이스에는 `diary` 스키마가 이미 있음. `dr_` 이름은 없음(2026-11-18 `DATABASE_URL`로 읽기 전용 접속해 조회함. 접속 주소는 출력하지 않음)
  - 이 데이터베이스는 Supabase Postgres임(`auth`, `storage` 스키마가 있음)
  - `diary` 스키마에는 `entries`(4행)와 `schema_migrations`(1행) 표가 있음. `entries`의 열은 일기, 감정, 공감 메시지, 위기 여부를 담는 꼴임
  - `diary_0904` 스키마도 있음. `diary_entries`(12행)와 `users`(1행) 표가 있음
  - `dr_`로 시작하는 표, 형식, 함수는 데이터베이스 전체에 없음
  - `dr_diary` 스키마도 없음. 따라서 `dr_diary`를 새로 만들어도 기존 스키마와 겹치지 않음
- `DATABASE_URL`은 Supabase MCP에 로그인된 계정의 프로젝트 2개(shopping-list-app, civil-complaint-practice)를 가리키지 않음(프로젝트 ID 포함 여부만 판정함)
  - 그러므로 Supabase MCP로는 이 데이터베이스를 관리할 수 없음. 마이그레이션은 `DATABASE_URL`로 직접 실행함
  - civil-complaint-practice는 일시 정지 상태이며, 2026-11-18 신 교수가 재가동하지 않기로 정함
- Next.js와 Auth.js의 현재 사용법은 확인하지 않았음
  - 이유: 문서 조회 도구 context7이 아직 인증되지 않음
  - 1단계에서 맡은 에이전트가 공식 문서로 확인함

## 3. 진행 방식

- 단계는 신 교수가 "진행하라"고 할 때만 시작함. 한 단계가 끝나면 결과를 보고하고 다음 지시를 기다림
- 만든 에이전트와 검토하는 쪽을 나눔. 예를 들면 코드는 개발 에이전트 3개가 만들고, 4단계에서 qa-engineer가 검토함
- 단계마다 끝을 판정하는 확인 방법을 정해 둠. 확인 방법을 모두 통과해야 그 단계를 끝난 것으로 봄
- 커밋과 깃허브 push는 신 교수가 지시할 때만 함(2026-11-18 신 교수 지시). 단계가 끝나도 지시 없이 커밋하지 않음
- 기존 `diary` 스키마는 어떤 단계에서도 읽기 밖의 작업(표 추가, 변경, 삭제, 행 쓰기)을 하지 않음. 쓰기는 `dr_diary` 스키마 안에서만 함
- 모든 에이전트는 `.env`를 열지 않고 변수 이름만 씀. 비밀 값은 코드, 로그, 커밋, 화면 쪽 코드에 넣지 않음

## 4. 단계별 계획

### 4.0 0단계: PRD

- product-manager가 이 문서 1장을 바탕으로 `docs/PRD.md`를 씀
  - 기능마다 사용자 이야기와 완료 기준을 적음. 예: "일기 한 줄을 저장하면 30초 안에 감정과 공감 메시지가 나옴"
  - 6장의 미결 가운데 PRD에서 정할 것(시간 제한 값, 두 모델이 모두 실패할 때의 동작, 상담 연락처 목록)에 안을 제시하고 신 교수에게 물음
  - 범위 밖 기능(일기 수정, 공유, 통계 그래프 등)을 따로 적어 둠
- 끝났는지 확인하는 법
  - `docs/PRD.md`에 1장의 요구가 모두 들어 있음. product-manager가 1장의 항목과 PRD의 절을 대응시킨 표를 첨부함
  - 신 교수가 PRD를 읽고 승인함

### 4.1 1단계: 뼈대

- backend-developer가 Next.js 프로젝트와 공통 약속을 만듦
  - Next.js 앱을 만들고, Auth.js로 구글 로그인만 동작하게 함
  - `dr_diary` 스키마와 `dr_entries` 표를 만드는 마이그레이션 SQL을 씀. 마이그레이션 기록이 필요하면 `dr_diary` 안에 따로 두고, 기존 `diary.schema_migrations`는 쓰지 않음. 표의 열(사용자 ID, 일기 내용, 감정, 공감 메시지, 위기 여부, 응답한 모델, 작성 시각)은 PRD에 맞춰 정함
  - 2단계의 3개 에이전트가 겹치지 않도록 API 형식(요청과 응답의 JSON)과 폴더별 담당을 `docs/CONTRACT.md`에 적음
  - `.env.example`에 필요한 변수 이름만 적음
- 마이그레이션은 `dr_diary` 스키마 안에서만 실행함
  - 실행 전에 SQL에 `dr_diary.` 밖의 대상(특히 기존 `diary` 스키마)이 없는지 qa-engineer가 읽어 확인함
  - 실행은 신 교수의 승인을 받은 뒤에 함
- 끝났는지 확인하는 법
  - `npm run build`가 성공함
  - 로컬에서 구글 로그인과 로그아웃이 됨
  - `dr_diary.dr_entries` 표가 생겼고, `diary` 스키마를 포함한 다른 스키마의 표 수와 행 수는 실행 전과 같음(실행 전후로 스키마별 표 수와 기존 표의 행 수를 조회해 비교함)

### 4.2 2단계: 백엔드, AI, 화면 동시 진행

- 3개 에이전트가 `docs/CONTRACT.md`의 약속에 따라 각자 맡은 폴더만 고침
  - backend-developer: 일기 저장 API와 지난 기록 조회 API를 만듦. 모든 조회와 저장은 서버에서 로그인한 사용자의 ID로 거름
  - ai-integration-specialist: OpenRouter 호출 모듈을 만듦. 첫 모델이 시간 안에 응답하지 않거나 오류를 내면 둘째 모델을 부름. 감정 분석과 공감 메시지의 프롬프트를 다듬음
  - frontend-developer: 일기 쓰기, 결과 보기, 지난 기록 보기 화면을 만듦. 2단계에서는 API 대신 가짜 데이터로 만듦
- 위기 표현은 2겹으로 찾음
  - 첫째, 위기 표현 목록으로 찾음. 왜냐하면 두 모델이 모두 실패해도 상담 연락처는 보여야 하기 때문임
  - 둘째, 모델에게 위기 여부를 함께 판정하게 함
  - 둘 가운데 하나라도 위기로 판정하면 상담 연락처를 보여 줌
  - 위기 표현 목록과 판정은 ai-integration-specialist가, 연락처를 보여 주는 화면은 frontend-developer가 맡음
- 끝났는지 확인하는 법
  - backend-developer: 사용자 A로 저장한 일기가 사용자 B의 조회에 나오지 않음(시험 코드로 확인함)
  - ai-integration-specialist: 실제 호출로 첫 모델의 응답을 받음. 첫 모델을 일부러 실패시켰을 때 둘째 모델의 응답을 받음. 입력과 출력 예를 보고에 포함함
  - ai-integration-specialist: 위기 예문 5개와 일반 예문 5개에서 위기 판정이 기대와 같음
  - frontend-developer: 휴대폰 폭(375px)과 데스크톱 폭에서 3개 화면이 깨지지 않음. 키보드만으로 일기를 쓰고 저장할 수 있음

### 4.3 3단계: 통합

- backend-developer가 3개 결과를 하나로 묶음
  - 일기 저장 API가 AI 모듈을 불러 감정, 공감 메시지, 위기 여부를 함께 저장함
  - frontend-developer가 화면의 가짜 데이터를 실제 API로 바꿈
  - 두 모델이 모두 실패하면 PRD에서 정한 대로 동작함
- 끝났는지 확인하는 법
  - 로컬에서 로그인 → 일기 저장 → 감정과 공감 메시지 확인 → 지난 기록 보기를 끝까지 따라 함
  - 위기 예문을 저장하면 상담 연락처가 나옴
  - `npm run build`가 성공함

### 4.4 4단계: QA

- qa-engineer가 만든 쪽과 따로 검토함
  - 기능 시험: PRD의 완료 기준을 하나씩 판정함
  - 오류 처리 검증: 빈 일기, 아주 긴 일기, 로그인하지 않은 요청, 다른 사용자의 일기 ID로 한 요청, 두 모델 모두 실패를 시험함
  - 보안 검토: 화면 쪽 코드와 커밋 기록에 비밀 값이 없는지, 마이그레이션과 앱의 SQL이 `dr_diary` 스키마 밖을 건드리지 않는지 확인함
  - 상담 연락처가 공식 자료와 같은지 확인함
- qa-engineer는 제품 코드를 고치지 않음
  - 문제를 심각도와 재현 방법과 함께 `docs/QA.md`에 적음
  - 고치는 일은 맡은 개발 에이전트가 하고, qa-engineer가 다시 시험함
- 끝났는지 확인하는 법
  - `docs/QA.md`에 심각도 높음과 중간인 문제가 0건임
  - 시험하지 못한 항목은 이유와 함께 5단계의 확인 목록으로 넘김

### 4.5 5단계: 배포

- backend-developer가 Vercel에 배포함
  - 깃허브 저장소를 Vercel 프로젝트에 연결함
  - Vercel에 환경 변수를 넣음. 값은 신 교수가 넣거나, 신 교수가 정한 방법으로 넣음
  - 구글 OAuth 설정에 배포 주소의 리디렉션 주소를 더함
  - 배포 전에 Vercel 함수의 시간 제한과 무료 모델의 응답 시간을 비교함
- qa-engineer가 배포한 앱에서 스모크 시험을 함
  - 4.3절(3단계: 통합)의 흐름을 배포 주소에서 끝까지 따라 함
  - 4단계에서 넘어온 확인 목록을 시험함
- 끝났는지 확인하는 법
  - 배포 주소에서 구글 로그인, 일기 저장, 공감 메시지, 지난 기록, 위기 안내가 모두 동작함
  - 다른 계정으로 로그인하면 앞 계정의 일기가 보이지 않음
  - 로컬 시험 통과만으로는 끝난 것으로 보지 않음. 배포 뒤 스모크 시험이 마지막 확인임

## 6. 미결

- 0단계 PRD에서 정할 것 세 가지와 일기 길이 상한은 2026-11-18 신 교수가 PRD의 제안안대로 승인함(`docs/PRD.md` 첫머리)
- `.env`에 구글 로그인 변수가 없음
  - Auth.js가 요구하는 `AUTH_SECRET`, `AUTH_GOOGLE_ID`, `AUTH_GOOGLE_SECRET` 3개가 모두 없음(2026-11-18 값을 출력하지 않는 스크립트로 변수 이름만 판정함)
  - 1단계 전에 신 교수가 구글 OAuth 클라이언트를 만들고, 신 교수가 정한 방법으로 3개 변수를 넣음
